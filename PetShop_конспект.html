Пет Шоп — конспект проекта

Магазин зоотоваров: каталог категорий, список товаров с фильтрами и сортировкой, страница товара, корзина и две формы для сбора заявок. React SPA обращается к небольшому API на Express + SQLite.

React 18 React Router 6 Redux Toolkit React Hook Form Axios CSS Modules Express 4 Sequelize 6 SQLite

01 Обзор

Архитектура

Два отдельных приложения, два отдельных dev-сервера. React-приложение никогда не обращается к базе данных напрямую — всё идёт через HTTP API.

Как это работает — на примере одного запроса

Открываем страницу «Категории». Что происходит по шагам, от клика до картинки на экране:

  1. Компонент Categories монтируется → срабатывает useEffect → вызывается api.get('/categories/all').
  2. Axios реально отправляет HTTP GET на http://localhost:3333/categories/all — это настоящий сетевой запрос, браузер уходит на другой порт.
  3. На бэкенде запрос проходит через middleware по порядку: cors пропускает его (разрешены все origin), доходит до роутера /categories.
  4. Обработчик роута вызывает Category.findAll() — Sequelize превращает это в SQL (SELECT * FROM Categories) и выполняет его на файле database.sqlite.
  5. Результат — обычные JS-объекты — уходит обратно как JSON через res.json(...).
  6. Promise у axios.get резолвится, setCategories(data) обновляет состояние компонента.
  7. React видит новое состояние и перерисовывает список — на экране появляются карточки категорий.

Зачем два отдельных сервера, а не один? Это стандартное разделение «фронтенд отдельно, API отдельно»: React ничего не знает про базу данных и SQL, он просто просит данные по HTTP. Такое разделение позволяет разрабатывать и деплоить их независимо, и именно так чаще всего построены реальные проекты — SPA на одном домене/порту, API — на другом.

Как это работает

React Router перехватывает клики по <Link>: вместо обычного перехода браузера (который бы перезагрузил всю страницу и заново скачал JS/CSS) он вызывает history.pushState — адрес в строке браузера меняется, но страница физически не перезагружается. React Router сравнивает новый путь со списком маршрутов и решает, какой компонент показать в этот момент.

Зачем нужен <Outlet/> в MainLayout: без него пришлось бы вставлять <Header/> и <Footer/> в каждую страницу отдельно. Так — они рендерятся один раз как обёртка, а <Outlet/> просто подставляет на своё место тот компонент, который сматчился с текущим путём. При переходе между страницами Header и Footer не перемонтируются заново, что и не нужно, — это чистый SPA-подход.

Почему * — последний в списке: React Router проверяет маршруты по порядку сверху вниз и берёт первое совпадение. * матчит вообще любой путь, поэтому если поставить его выше — он «съест» все остальные маршруты и они никогда не сработают.

Зачем такое разделение

Принцип простой: если один и тот же кусок интерфейса (карточка товара, крошки, сетка с фильтрами) нужен на нескольких страницах — он выносится в отдельный компонент один раз, а страницы его просто переиспользуют. Например, ProductGrid с фильтром цены и сортировкой используется на страницах «Категория», «Все товары» и «Все скидки» — логика фильтрации написана один раз, а не скопирована трижды. Если завтра понадобится добавить ещё один фильтр — правится один файл, а не три.

Состояние — Redux Toolkit

Redux используется ровно для одной вещи — корзины. Всё остальное (загруженные товары, фильтры, черновики форм) — локальный useState. Корзину нужно читать/писать из несвязанных веток дерева — Header, каждая карточка товара, страница товара, элемент корзины, страница корзины — поэтому она поднята в стор, а не прокидывается через пропсы.

store.js
  • configureStore({ reducer: { cart } })
  • store.subscribe() пишет cart.items в localStorage['cart'] при каждом изменении
  • <Provider store={store}> оборачивает <App/> в index.js
cartSlice.js
  • начальное состояние читает localStorage['cart'] при загрузке
  • addItem — объединяет количество, если id уже есть в корзине
  • removeItem, updateQuantity (ограничено минимумом 1), clearCart
Как это работает — на примере клика «Add to cart»
  1. Пользователь жмёт кнопку → вызывается dispatch(addItem({ id, title, price, ... })).
  2. addItem — это «action creator» из createSlice: он не меняет состояние сам, а создаёт обычный объект-действие вида { type: 'cart/addItem', payload: {...} }.
  3. dispatch отправляет этот объект в store. Store вызывает reducer-функцию cartSlice с текущим состоянием и этим action.
  4. Внутри reducer выглядит так, будто состояние мутируется напрямую (existingItem.quantity += quantity) — это работает благодаря библиотеке Immer, которую createSlice использует под капотом: она позволяет писать «мутирующий» код, а сама на самом деле создаёт новый неизменяемый (immutable) объект состояния.
  5. Store сохраняет новое состояние и оповещает всех подписчиков. Все компоненты с useSelector(state => state.cart...) — Header, эта же карточка товара, страница корзины — перерисовываются с новыми данными.
  6. Параллельно срабатывает store.subscribe() из store.js — он ни к чему конкретно не привязан, просто слушает вообще любое изменение store, и пишет актуальный cart.items в localStorage.

Почему именно Redux, а не просто поднять состояние в App.js и прокидывать пропсами: корзину читают и меняют компоненты, которые не являются предками/потомками друг друга напрямую (Header — это часть layout, а карточка товара — глубоко внутри страницы). Пропсами это состояние пришлось бы прокидывать через десяток промежуточных компонентов, которым оно самим не нужно. Redux даёт любому компоненту прямой доступ к нужному кусочку состояния через useSelector, без «прострела» пропсами насквозь дерева.

Формы и валидация — React Hook Form

И форма заказа в корзине, и форма скидки на главной используют react-hook-form, настроены одинаково:

ЧастьЧто делает
register('field', rules)подключает поле к RHF; используемые правила: required, minLength (имя), pattern (регулярка для телефона/email)
shouldUseNativeValidation: trueпередаётся в useForm() — RHF вызывает встроенный Constraint Validation API браузера, поэтому невалидные поля показывают нативную подсказку браузера с текстом от RHF, без кастомного UI ошибок
handleSubmit(onSubmit)запускает валидацию, вызывает onSubmit только если форма валидна
watch(callback)подписывается на изменение каждого поля, чтобы зеркалить черновик в localStorage
reset()очищает форму обратно до пустой после успешной отправки
Как это работает под капотом

register() — почему поля не завязаны на useState. {...register('name', {...})} раскрывается в набор пропсов: ref, name, onChange, onBlur. ref — это прямая ссылка на DOM-элемент инпута. React Hook Form читает значение поля напрямую из DOM через эту ссылку, а не хранит его в состоянии React. Это «неконтролируемые» (uncontrolled) инпуты: компонент не перерисовывается на каждое нажатие клавиши, что быстрее, чем держать отдельный useState на каждое поле.

Как именно всплывает нативная подсказка браузера. При сабмите handleSubmit проверяет значения по правилам (required, pattern и т.д.). Если поле невалидно, а включён shouldUseNativeValidation, RHF вызывает input.setCustomValidity('Name is required') — это встроенный браузерный API, который помечает поле как невалидное с конкретным текстом. Дальше браузер сам показывает свой «пузырь» с этим текстом и ставит фокус на поле — никакого кастомного JSX для ошибок писать не нужно.

Зачем watch(callback), а не просто watch(). Вызов watch() без аргументов подписывает компонент на все изменения и вызывает лишний ре-рендер на каждую клавишу. Форма с колбэком (watch((values) => {...})) — это просто подписка «в фоне»: колбэк вызывается на каждое изменение, но сам компонент не перерисовывается из-за этого. То есть запись в localStorage происходит без побочной нагрузки на рендер.

Итог: полная перезагрузка страницы сохраняет содержимое корзины и любую недописанную форму — ничего не теряется, пока не сработает соответствующая успешная отправка.

Как это работает и почему именно так

localStorage — это встроенное в браузер хранилище «ключ → строка», привязанное к конкретному домену (origin), которое переживает закрытие вкладки и даже перезапуск браузера. Хранит только строки, поэтому объекты/массивы всегда проходят через JSON.stringify перед записью и JSON.parse при чтении.

Почему чтение происходит не в useEffect, а прямо в начальном состоянии (loadItems() вызывается прямо внутри useState(loadItems) / как initialState слайса): useEffect выполняется после первого рендера. Если бы корзина сначала рендерилась пустой, а потом — уже после эффекта — подгружались данные из localStorage, пользователь на долю секунды увидел бы «пустую» корзину, которая тут же дёргано заполняется. Чтение сразу в начальном состоянии убирает это мигание.

Почему запись происходит в одном месте (store.subscribe()), а не в каждом компоненте, который меняет корзину: так гарантированно ловится вообще любое изменение стора, независимо от того, из какого компонента был вызван dispatch — не нужно помнить «допиши localStorage.setItem» в каждом новом месте, где меняется корзина.

API-слой

src/api/axios.js экспортирует один настроенный инстанс:

axios.create({ baseURL: 'http://localhost:3333' })

Каждая страница запрашивает данные напрямую через useEffect(() => { api.get(...) }, [deps]) — отдельного слоя данных или библиотеки кеширования нет. Реальные вызовы с фронтенда:

ВызовИспользуется в
GET /categories/allHome (виджет), страница Categories
GET /categories/:idCategoryProducts, ProductDetails (запасной вариант названия категории для хлебных крошек)
GET /products/allAllProducts, AllSales, виджет Sales

POST /order/sendотправка CartPage
Зачем общий инстанс, а не просто fetch() в каждом месте

Без общего инстанса пришлось бы в каждом компоненте писать полный адрес http://localhost:3333/... — а если бэкенд переедет на другой хост или порт (например, при деплое), пришлось бы менять его в десятке файлов. Так — baseURL задан один раз, и во всех запросах используется просто относительный путь: api.get('/products/all').

Про поле "proxy" в package.json: оно относится только к dev-серверу Create React App (тому, что запускается через npm start) — если бы фронтенд делал запросы на относительные пути (например, просто /categories/all без адреса), CRA сам бы перенаправил их на localhost:3333, чтобы не ловить CORS при разработке. В этом проекте оно фактически не используется: baseURL в axios уже абсолютный (http://localhost:3333), поэтому запросы и так идут напрямую, а CORS открыт на бэкенде (cors({origin:'*'})). Хороший момент, если препод спросит «а зачем тут proxy» — можно честно сказать, что он остался как задел, но в реальности не требуется.

03 Backend

Express + Sequelize

Отдельной папки controllers нет — каждый файл в routes/ содержит обработчики напрямую. Нет авторизации, нет конфигурации через env: всё захардкожено (порт 3333, путь к файлу SQLite).

Статические картинки — express.static('public') раздаёт /category_img/*.jpeg и /product_img/*.jpeg напрямую; фронтенд собирает URL как API_BASE_URL + product.image.

Как это работает и почему так

Что вообще делает Sequelize. Это ORM (Object-Relational Mapping) — слой, который переводит вызовы JS-методов в SQL-запросы и обратно превращает строки таблиц в обычные JS-объекты. Вместо ручного написания SELECT * FROM Products WHERE categoryId = 1 пишется Product.findAll({ where: { categoryId: 1 } }) — Sequelize сам собирает нужный SQL под используемую СУБД (здесь — SQLite).

Как работает Category.hasMany(Product). Эта одна строчка в index.js говорит Sequelize: «у одной категории может быть много товаров». При следующем sequelize.sync() он автоматически добавляет колонку categoryId в таблицу Products — это и есть внешний ключ (foreign key). Формально связь ещё даёт готовые методы вроде category.getProducts(), но в этом проекте они не используются — товары по категории ищутся вручную через Product.findAll({where:{categoryId}}), то есть связь тут используется только ради самой колонки categoryId.

Почему порядок миддлваров важен. Express выполняет миддлвары строго в том порядке, в котором они добавлены через app.use(). В этом проекте express.json() (парсер JSON-тела запроса) стоит после подключения роутеров — значит, к моменту, когда запрос доходит до обработчика в routes/order.js, req.body ещё не распарсен. На практике это не ломает приложение только потому, что order.js и sale.js и так не читают req.body — но если бы в будущем понадобилось реально сохранять данные заказа, это всплыло бы как баг: тело запроса пришло бы undefined.

sequelize.sync() при каждом старте сервера сверяет модели с реальной структурой SQLite-файла и создаёт недостающие таблицы. Формальных миграций (отдельных файлов с историей изменений схемы) в проекте нет — это самый простой вариант, подходящий для учебного проекта, но не для продакшена с уже накопленными данными.

О чём стоит уметь рассказать

  • Почему Redux только для корзины: это единственный кусок состояния, который читается и пишется из несвязанных веток дерева компонентов (Header, пять разных страниц-списков, страница товара, корзина). Всё остальное остаётся локальным, потому что больше ничему не нужно «дотягиваться» так далеко.
  • Хлебные крошки отражают реальную навигацию, а не структуру данных. ProductCard передаёт breadcrumbTrail через <Link state={{...}}>; ProductDetails считывает его обратно через useLocation(). Прямой переход по ссылке (без state роутера) откатывается к восстановлению цепочки через categoryId самого товара.
  • Нативная валидация вместо кастомного текста ошибок. shouldUseNativeValidation — осознанный выбор, чтобы UX обеих форм совпадал со встроенными подсказками браузера, а не с самописными абзацами ошибок.
  • Вложенным flex-контейнерам нужен явный min-width:0. Flex-элемент, который сам является flex-контейнером (галерея товара), имеет автоматический минимальный размер по контенту, который может вытолкнуть его за пределы отведённого места — решение было именно в min-width:0, а не в изменении flex-basis.
  • Backend никогда по-настоящему не сохраняет заказ. /order/send и /sale/send — заглушки: ничего не валидируют и всегда возвращают успех. Сама корзина живёт только в Redux + localStorage.
  • Автосброс кнопок. «Add to cart» → «Added» и «Get a discount» → «Request submitted» автоматически возвращаются обратно через 2 секунды через setTimeout, сохранённый в ref, и очищаются при размонтировании, чтобы не обновлять состояние уже размонтированного компонента.

Запуск локально

Backend — порт 3333
cd backend
npm install
node index.js
Frontend — порт 3000
cd frontend
npm install
npm start

Поле "proxy": "http://localhost:3333" в frontend/package.json влияет только на dev-сервер npm start; само приложение всегда обращается по полному адресу http://localhost:3333 через инстанс axios.
